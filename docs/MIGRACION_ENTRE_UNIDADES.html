Propósito y modalidades

La unidad destino debe aprobar hospedaje, DNS, segmento de red, tratamiento de tickets y cuentas administrativas. Distinguir:

  1. Instancia nueva: mismo software, base y cuentas independientes; no copiar datos personales del origen.
  2. Traslado de historial: transferir SQLite con tickets, eventos, identificadores, correos, descripciones y hashes de contraseña. Requiere autorización del dueño de datos, transferencia cifrada, custodio y retención aprobados.

No copie lan-session-secret.txt. El destino genera uno propio; se invalidan cookies previas, pero no tickets ni hashes si la SQLite autorizada se migra.

No extender el piloto HTTP a otra sede/VLAN. El transporte no cifra tickets ni credenciales. Para otras subredes, use HTTPS institucional y reglas aprobadas.

Preflight obligatorio

  • FQDN aprobado, registro A/PTR y hostname del nuevo host.
  • IP estática/reservada, prefijo, gateway, DNS, VLAN y perfil DomainAuthenticated.
  • CIDR clientes autorizados, rutas inter-VLAN y puertos de firewall aprobados.
  • Certificado TLS institucional con SAN del FQDN destino y EKU Server Authentication para otras redes.
  • Fuentes de paquetes aprobadas para Python, URL Rewrite y ARR.
  • Decisión del propietario sobre base vacía o traslado autorizado; responsable de backup y rollback.

No reutilice la IP de origen sin asignación expresa de Redes. No incruste credenciales de dominio en scripts.

Preparar el servidor destino

  1. Instale Windows aprobado y parches institucionales.
  2. Asigne hostname aprobado, únalo al dominio y configure la IP estática mediante Redes.
  3. Valide DNS, gateway, perfil Domain y resolución del FQDN desde clientes.
  4. Copie código verificado por canal aprobado. No publique el proyecto como share SMB o sitio estático: el portal necesita API.
  5. Instale Python 3.13/versión aprobada y cree `.venv` desde repositorio interno aprobado.
  6. Revise `deploy/run-lan-http.ps1`: cambie `$hostAddress` y el `RemoteAddress` a valores asignados. La copia actual está fijada a `192.0.2.10` y `192.0.2.0/24`.
  7. El modo HTTP solo puede usarse en LAN destino confiable con autorización; otras redes requieren TLS.

Instancia nueva, sin datos del origen

Recomendada cuando cada unidad debe conservar sus propios casos.

  1. No copie `instance/helpdesk.sqlite3`; use base vacía del destino.
  2. El lanzador crea el secreto local en C:\ProgramData\MesaSoporteS6 y aplica ACL SYSTEM/Administradores.
  3. Desde PowerShell elevado, registre e inicie la tarea:
Set-Location 'D:\HELP DESK TELEMATICA'
Set-ExecutionPolicy -Scope Process Bypass
.\deploy\install-lan-task.ps1
Start-ScheduledTask -TaskName MesaSoporteS6-LAN
  1. Cree administrador de destino mediante `server.py create-admin` usando el entorno virtual y contraseña aprobada.
  2. Pruebe portal, login, firewall y una solicitud marcada como prueba antes de anunciar la URL.

Mover historial autorizado

Backup de origen

  1. Anuncie ventana de mantenimiento y pare la recepción.
  2. Detenga la tarea y confirme que el listener desaparezca:
Stop-ScheduledTask -TaskName MesaSoporteS6-LAN
Get-NetTCPConnection -State Listen -LocalPort 8080 -ErrorAction SilentlyContinue
  1. La SQLite usa WAL. No copie el archivo mientras el servicio escribe; haga backup transaccional con `sqlite3.Connection.backup()`.
  2. Compruebe `PRAGMA integrity_check` (debe indicar `ok`), recuentos, fecha, checksum, responsable y autorización.
  3. Cifre el backup con medio institucional y entregue al custodio. No use correo, WhatsApp, nube pública ni SMB no aprobado.

Restauración de destino

  1. Detenga la tarea destino y restrinja `instance` a SYSTEM/Administradores.
  2. Transfiera el backup aprobado por canal cifrado; valide integridad y recuentos antes de reemplazar la base del destino.
  3. No copie el secreto de origen; el destino genera clave propia. Los hashes de usuarios se conservan si se mueve SQLite; las sesiones web antiguas no.
  4. Inicie destino solo cuando origen esté detenido. Dos instancias escribiendo en copias separadas producen historiales divergentes.
  5. Pruebe con usuarios autorizados y backup nuevo. Si falla, cierre destino y ejecute rollback acordado.

TLS y acceso entre unidades

Para tráfico fuera del segmento local, solicite certificado de servidor en la CA institucional para el FQDN destino, con SAN DNS, Server Authentication y clave privada protegida localmente.

La plantilla de solicitud `deploy/iis-cert-request.inf` contiene hoy el host actual; actualice sujeto y SAN antes de generar una CSR en el destino. Envíe solo el CSR por el proceso PKI. Si RPC a la CA está bloqueado, entregue la solicitud al equipo de PKI. No use el certificado SolarWinds, autofirmados ignorados por usuarios ni claves exportadas de otro host.

IIS/ARR/URL Rewrite con TLS requiere instalar módulos desde fuente corporativa, enlazar certificado al FQDN y validar cadena desde clientes. `web.config` fuerza HTTPS y reenvía a Waitress en loopback, pero el servicio de producción HTTPS aún requiere preparar una tarea/servicio backend distinto del lanzador LAN; no basta instalar el certificado.

Tras validar TLS, abra solo TCP 443 desde CIDR autorizados y cierre TCP 8080 del piloto. Nunca publique Waitress directamente entre VLAN.

DNS, corte y rollback

  1. Redes crea el A record (y PTR si corresponde); usuarios accederán con el FQDN, no con IP.
  2. Detenga origen, haga backup final, restaure/verifique destino y luego cambie DNS/enlaces.
  3. No mantenga ambas instancias recibiendo tickets. Si destino aceptó tickets reales, no sobrescriba una base con otra; reconcilie bajo el dueño de datos.
  4. Para rollback, cierre recepción destino, conserve evidencia/backup y revierta DNS solo si origen no perdió casos nuevos. Quite únicamente bindings y reglas creadas por el cambio.

Criterios de aceptación

  • ☐ Aprobaciones de dueño de datos, Redes y Seguridad.
  • ☐ FQDN/IP y tarea corresponden al destino aprobado.
  • ☐ Firewall limita origen y puerto según matriz autorizada.
  • ☐ HTTPS es confiable para cada segmento autorizado; 8080 no está expuesto entre sedes.
  • ☐ SQLite íntegra y recuentos coinciden si se migró historial.
  • ☐ Ticket de prueba único visible en consola autenticada.
  • ☐ Backup/restore y responsable de rollback probados.
